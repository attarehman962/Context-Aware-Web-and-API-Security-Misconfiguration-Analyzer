# 02 — Architecture

## High-level flow

```
Target URL
    ↓  (validation + SSRF guard)
Safe HTTPS connection  (httpx async engine)
    ↓
Endpoint discovery  (crawler — 4 strategies)
    ↓
Endpoint context classification  (NLP — Contribution 1)
    ↓
HTTP response collection
    ↓
58 security checks
    ↓
Response-body classification  (Contribution 3)
    ↓
Finding generation  →  CVSS base × context multiplier + response bonus = final score
    ↓
Attack-chain correlation  (Contribution 2)
    ↓
PostgreSQL  →  Reports (JSON/CSV/HTML/PDF)  →  REST API + SSE live status
    ↓
Next.js frontend
```

## Process topology

CAWASMA runs as cooperating processes so that a scan never blocks the API:

```
          HTTP / SSE
Browser  ─────────────────▶  FastAPI (async)  ◀────────┐
(Next.js)                       │  creates QUEUED scan row │ SSE reads progress
                                │  enqueues job            │
                                ▼                          │
                            Redis (broker)                 │
                                │                          │
                                ▼                          │
                          Celery worker                    │
                                │  runs the scan pipeline  │
                                ▼                          │
                           PostgreSQL  ────────────────────┘
```

- **FastAPI** accepts the scan, writes a `QUEUED` row, and returns immediately.
- **Celery worker** (separate process) runs the full pipeline with
  `asyncio.run()`.
- The worker writes progress per stage to the scan row (`progress`,
  `current_stage`, `progress_detail`). `GET /api/scan/{id}/events` (SSE) re-reads
  that row and sends a `status` event whenever it changes, so live status needs
  no second channel between the worker and the API.
- The worker writes endpoints, findings, chains, TLS info and an insight to
  **PostgreSQL**.

A lightweight alternative exists: setting `RUN_SCANS_INLINE=true` runs the scan as
an in-process asyncio task, so the whole product works without Celery/Redis — handy
for simple deployments and demos.

## Layering (separation of concerns)

| Layer | Location | Responsibility |
|-------|----------|----------------|
| API | `backend/app/api/` | Routes + Pydantic schemas; never returns raw ORM objects |
| Services | `backend/app/services/` | Orchestration: scan creation, pipeline driver, persistence, reports, insights, LLM |
| Scanner | `backend/app/core/` | Pure, DB-free logic: engine, crawler, classifiers, 58 rules, CVSS, chains, TLS |
| Database | `backend/app/db/` | SQLAlchemy models, async session, base |
| Worker | `backend/app/workers/` | Celery app + `run_scan` task |
| Utils | `backend/app/utils/` | Validation, SSRF/security, redaction, logging |

The **scanner is deliberately database-free** — every rule is a pure function
`detect(ctx) -> RawFinding | None`. This makes the 58 checks and the three
contributions trivially unit-testable in isolation, which is why the suite can
cover them deterministically without a live target.

## Technology choices (why each)

- **FastAPI** — async-native (needed for concurrent httpx requests), automatic
  OpenAPI docs at `/docs`, first-class Pydantic validation. Chosen over Flask for
  native async and built-in schema/validation.
- **httpx** — async HTTP client with fine control over redirects, timeouts and
  streaming (needed for response-size caps and per-hop SSRF re-checks).
- **PostgreSQL + SQLAlchemy (async/asyncpg)** — a relational schema fits the data
  (scans → endpoints → findings → chains with many-to-many links and cascades);
  the ORM parameterizes queries, preventing SQL injection.
- **Alembic** — versioned, autogenerated migrations; no manual table creation.
- **Celery + Redis** — moves long scans to the background; Redis doubles as the
  broker and the progress pub/sub bridge.
- **sentence-transformers (`all-MiniLM-L6-v2`)** — optional semantic layer for the
  endpoint classifier; the classifier falls back to an explainable keyword layer
  when the model isn't installed.
- **WeasyPrint + Jinja2** — professional PDF/HTML reports.
- **Next.js** — the separate frontend consuming the REST contract and the SSE stream.

## Safety architecture (the scanner scans safely, and protects itself)

- **HTTPS-only** target validation (scheme, hostname, port, fragments, redirects).
- **SSRF protection** — the hostname is resolved and the **resulting IP** is
  validated (loopback, private, link-local, reserved, cloud-metadata blocked);
  every redirect hop is re-checked. String comparison alone is never trusted.
- **Bounded requests** — timeout, max response size, max endpoints, max crawl
  depth, max redirects, concurrency limit (all configurable).
- **Redaction** — secrets are masked before anything is logged, stored, or put in
  a report.
